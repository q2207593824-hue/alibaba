# 性能优化说明

## 问题描述

系统在本地运行时存在以下性能问题：
1. **登录太慢**：需要 10-20 秒才能完成
2. **管理员会员列表无数据**：刷新后看不到任何用户
3. **系统整体响应慢**：页面加载、接口调用都很慢

---

## 根本原因

系统默认启用了**云端会员模式**（`MEMBERSHIP_POINTS_SOURCE=cloud`），在以下场景会请求云端 API（`https://echo-yiwu.cloud`）：

| 操作 | 云端请求 | 超时设置（修复前） | 症状 |
|---|---|---|---|
| 登录 | `/auth/login` | 20 秒 | 云端不可达时等 20 秒超时 |
| 查看会员中心（/me） | `/me` | 8 秒 | 加载个人信息慢 |
| 管理员查询用户列表 | `/admin/users` | 2 秒 | 超时返回空数组 `[]` |
| 扣积分 | `/points/transactions` | 8 秒 | 产品优化等功能慢 |

**当云端不可达时**（如网络不通、服务器宕机、被防火墙阻断），每个请求都要等到超时，累加起来非常慢。

---

## 已实施的修复

### 修复 1：缩短超时时间（代码层面）

修改了 `backend/app/services/membership_service.py` 第 43-48 行：
```python
# 修复前：读取超时 20 秒
_CLOUD_LOGIN_HTTP_TIMEOUT = (5, 20)

# 修复后：读取超时 8 秒（与 /me 接口一致）
_CLOUD_LOGIN_HTTP_TIMEOUT = (3, 8)
```

### 修复 2：管理员列表兜底返回本地数据

修改了 `list_users_admin()` 函数（第 3960-3980 行）：
```python
# 修复前：云端不可达时返回空列表
return _merge_cloud_points_into_admin_users(local_rows) if enabled else local_rows

# 修复后：云端合并失败时仍返回本地数据
if enabled:
    try:
        return _merge_cloud_points_into_admin_users(local_rows)
    except Exception as e:
        logger.warning(f"云端用户列表合并失败，返回本地数据: {e}")
        return local_rows  # ← 兜底返回本地数据
else:
    return local_rows
```

### 修复 3：创建本地环境配置文件（推荐）

新增了 `backend/.env` 文件，**禁用云端模式**，所有数据使用本地 SQLite：
```bash
# 使用本地会员库
MEMBERSHIP_POINTS_SOURCE=local

# 禁用管理员列表的云端合并
MEMBERSHIP_ADMIN_USERS_CLOUD_MERGE=no

# 缩短超时时间
CLOUD_LOGIN_READ_TIMEOUT_SEC=5
```

## 使用建议

### 场景 1：纯本地开发/单机使用（推荐）

**适用**：不需要多机同步，数据只在本机使用

**配置**：使用已创建的 `backend/.env` 文件（已默认配置好）

**效果**：
- ✅ 登录秒级响应（不请求云端）
- ✅ 管理员列表正常显示
- ✅ 所有操作流畅，无网络依赖

**如何启动**：
```bash
cd backend
python -m app.main
```
FastAPI 会自动加载 `.env` 文件。

---

### 场景 2：云端模式（多机同步）

**适用**：需要多台机器共享会员数据、积分余额

**前提**：
1. 云端服务（`echo-yiwu.cloud`）可访问
2. 配置了 `admin_api_key`

**如何启用**：
删除或修改 `backend/.env` 文件：
```bash
# 启用云端积分模式
MEMBERSHIP_POINTS_SOURCE=cloud

# 启用云端同步
MEMBERSHIP_CLOUD_SYNC_ENABLED=1
```

**效果**：
- ✅ 多机同步会员数据
- ⚠️ 需要网络连接，云端不可达时会降级到本地

## 常见问题

### Q1：启用本地模式后，会员数据会丢失吗？
**A**：不会。本地模式只是不请求云端 API，所有数据仍然保存在本地 SQLite（`backend/data/membership.db`）。如果之前使用云端模式，本地已经有缓存数据。

### Q2：本地模式下能绑定店铺吗？
**A**：可以。绑定店铺的流程（浏览器登录、Cookie 保存、采集公司信息）都在本地完成，不依赖云端。唯一的差异是绑定后不会同步到云端（如果你有多台机器，需要在每台机器上分别绑定）。

### Q3：我想恢复云端模式怎么办？
**A**：修改 `backend/.env` 文件，改为：
```bash
MEMBERSHIP_POINTS_SOURCE=cloud
```
或者直接删除 `.env` 文件，系统会使用默认配置。

### Q4：如何确认当前是哪种模式？
**A**：启动后端后，查看 console 输出的第一行：
- `use_cloud_points=False` → 本地模式 ✓
- `use_cloud_points=True` → 云端模式

### Q5：云端合并 company_name 的修复还生效吗？
**A**：生效。修复代码（`_merge_cloud_points_into_admin_users` 里新增的字段合并逻辑）仍然保留。当你启用云端模式且云端可达时，公司名称会自动同步。在本地模式下，因为不请求云端，所以合并逻辑不会被调用，但这不影响本地数据的显示。

## 技术细节

### 云端模式的判断逻辑

系统通过以下优先级判断是否使用云端：

1. **环境变量** `MEMBERSHIP_POINTS_SOURCE`
   - `local` → 本地模式（不请求云端）
   - `cloud` → 云端模式（默认）

2. **快速可达性检测**
   - 启动时会 ping 云端 `/health`（超时 1 秒）
   - 如果不可达，自动降级到本地模式

3. **运行时兜底**
   - 即使配置了云端模式，单个请求超时/失败时会降级返回本地缓存数据

### 缓存策略

云端模式下，以下数据会被缓存到本地，缓解云端不稳定的影响：

| 数据 | 缓存位置 | TTL |
|---|---|---|
| 用户信息（/me） | 内存 + SQLite | 60 秒 |
| 管理员用户列表 | 内存 | 60 秒 |
| 积分余额 | SQLite `user_points_accounts` | 实时更新 |

## 总结

- **问题根源**：云端不可达时，超时累加导致系统响应慢
- **核心修复**：缩短超时 + 兜底返回本地数据 + 提供本地模式开关
- **推荐配置**：本地开发使用 `MEMBERSHIP_POINTS_SOURCE=local`（已配置好）
- **验证方法**：重启后端，登录测试，查看管理员列表

修复后，系统在本地模式下应该非常流畅（秒级响应）。
